Фрактальность обещает: структура повторяется на всех уровнях. Этот раздел показывает, как это устроено на практике — как выглядит домен, когда из него стоит выносить подмодуль и как модули общаются друг с другом, не ломая границы.

## 🧩 Домен: верхний уровень

![Структура домена](/domain.png)

Домен — это модуль верхнего уровня внутри `routes/`. Он отвечает признакам:

- **Задаётся бизнесом, а не техникой.** Домен «корзина» существует потому, что корзина есть в требованиях, — а не потому, что так удобно разложить компоненты.
- **Понятен всем участникам.** Разработчик, менеджер и заказчик одинаково понимают, что лежит в `cart/` — им не нужно знать архитектуру, только бизнес.
- **Владеет своим кодом целиком.** От разметки страницы до запросов к базе: изменения фичи не выходят за пределы одной папки.
- **Определяет структуру приложения.** Список папок в `routes/` — это карта продукта. Новый раздел требований — новый домен.

Граница домена проходит по границе фичи. Если изменение требования «доставка считается от содержимого корзины» затрагивает два домена — это нормально: вы меняете контракт между ними, а не смешиваете их код. Как именно — в [разделе о взаимодействии](#-взаимодействие-между-модулями) ниже.

## 🪆 Подмодули

Когда домен растёт, его части выносятся в подмодули. У подмодула два вида:

| Вид | Папка | Роутинг | Когда использовать |
|-----|-------|---------|--------------------|
| **Публичный** | `cart/items/` | есть: `/cart/items` | Часть домена со своей страницей или API |
| **Приватный** | `cart/_checkout/` | нет: `_` прячет от роутера | Декомпозиция больших кусков логики без собственного URL |

У подмодуля — та же структура, что и у домена: своя модель, свой контроллер, свои типы. Фрактальность в действии: открыв `cart/items/`, вы видите то же устройство, что и в `cart/`, только масштаб меньше.

<Aside type="tip">

Не выносите подмодуль заранее. Сначала логика живёт в файлах домена; когда файл разросся или кусок стал самодостаточным («оплата внутри корзины»), — тогда выносите. Иначе вы получите структуру ради структуры.

</Aside>

### Полное дерево домена

```text
src/routes/
└── cart/                      # домен «корзина»
    ├── +page.svelte           # страница корзины
    ├── +page.server.ts        # server load
    ├── +server.ts             # HTTP-роут: действия
    ├── rpc.ts                 # API для других доменов
    ├── client.ts              # браузерные вызовы
    ├── model.server.ts        # операции с данными
    ├── controller.svelte.ts   # реактивное состояние
    ├── schema.ts              # таблицы ORM
    ├── types.ts               # типы домена
    ├── templates.ts           # шаблоны форм
    ├── constants.ts           # константы, enum
    ├── policy.ts              # правила доступа
    ├── utils.ts               # хелперы модуля
    ├── index.ts               # публичный API
    ├── ui/                    # внутренние компоненты
    │   ├── CartWidget.svelte
    │   ├── CartItemCard.svelte
    │   └── CheckoutForm.svelte
    │
    ├── _checkout/             # приватный подмодуль: без URL
    │   ├── rpc.ts
    │   ├── model.server.ts
    │   ├── controller.svelte.ts
    │   ├── types.ts
    │   ├── constants.ts
    │   ├── policy.ts
    │   ├── index.ts
    │   └── ui/
    │       └── PaymentStep.svelte
    │
    └── items/                 # публичный подмодуль: /cart/items
        ├── +page.svelte
        ├── +page.server.ts
        ├── rpc.ts
        ├── model.server.ts
        ├── controller.svelte.ts
        ├── types.ts
        ├── constants.ts
        ├── policy.ts
        ├── index.ts
        └── ui/
            └── ItemList.svelte
```

Имена файлов приведены для SvelteKit — в Next.js и Nuxt они называются по конвенции фреймворка (таблица соответствия — в [основных концепциях](/02-core-concepts/#-framework-agnostic)). Структура и роли при этом не меняются.

## 🔄 Взаимодействие между модулями

Границы доменов существуют, чтобы изменения в одном месте не ломали другое. Правило одно: **домен общается с соседями только через их `rpc.ts`**.

Публичный API модуля — это `rpc.ts` и `index.ts`, который его реэкспортирует. Всё остальное — модель, repo, контроллер — внутренности: их можно переименовывать и переписывать, не спрашивая соседей.

### Как выглядит нарушение

```ts
// ❌ routes/orders/model.server.ts
import { getProductById } from "$routes/products/model.server";
```

Домен `orders` полез в модель домена `products`. Теперь переименование функции в `products` ломает сборку `orders`, а чтение чужого `model.server.ts` тянет за собой серверные зависимости. Связанность, от которой архитектура и защищала.

### Как правильно

```ts
// ✅ routes/orders/model.server.ts
import { getProductById } from "../products/rpc";
```

`rpc.ts` домена `products` публикует функции для соседей: каждая валидирует вход и вызывает одну функцию модели. Внутри `products` можно делать что угодно — внешний контракт остаётся стабильным.

Запреты на импорты между доменами:

- ❌ `model.server.ts` чужого домена
- ❌ `repo/` чужого домена
- ❌ контроллер и stores чужого домена
- ✅ `rpc.ts` — единственная дверь

<Aside type="note">

А если нужен общий код, а не чужой? Компонент, который нужен нескольким доменам, переезжает из доменного `ui/` в `lib/ui/`. Глобальное состояние — в `lib/universal/stores/`. Общая логика — в `lib/`. Общее правило: «нужно одному домену — живёт в домене, нужно многим — живёт в lib».

</Aside>

## 🛠️ Создание домена с нуля

Порядок шагов повторяет движение данных снизу вверх: от источника данных к разметке.

<Steps>

1. **Создайте папку в `routes/`**

   Имя — из требований бизнеса: `cart`, `auth`, `orders`. Путь и имена файлов роутинга зависят от фреймворка: `src/routes/cart/` в SvelteKit, `app/cart/` в Next.js, `pages/cart/` в Nuxt.

2. **Опишите типы**

   `types.ts` — сущности домена (`CartItem`, `Cart`). Если есть ORM, рядом `schema.ts` с таблицами.

3. **Напишите модель**

   `model.server.ts` — операции с данными через repo: `getCart`, `addToCart`. Без HTTP и без UI.

4. **Опубликуйте API**

   `+server.ts` — HTTP-роут для браузера, `rpc.ts` — функции для соседних доменов. Каждый обработчик валидирует вход и вызывает одну функцию модели.

5. **Соберите контроллер**

   `controller.svelte.ts` (или `stores.ts`) — реактивное состояние, обработчики действий, вызовы `client.ts`.

6. **Сделайте страницу**

   `+page.server.ts` — load-функция с начальными данными (создавайте, даже если она пустая — пригодится). `+page.svelte` — разметка, только импорты контроллера.

7. **Экспортируйте API и проверьте импорты**

   `index.ts` реэкспортирует публичный API. Прогоните новый код по [чеклисту из раздела 06](/06-faq-checklist/) — особенно правила импортов между слоями.

</Steps>

Тот же порядок использует AI-агент со [скиллом FDA](/07-qwen-code-skill/) — он собирает домен по этим шагам и сам проверяет направление зависимостей.
