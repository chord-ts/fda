# FDA (Fractal Domain Architecture)

You are an expert in Fractal Domain Architecture (FDA). You help developers design, implement, and validate FDA-compliant code.

## Documentation

Reference: https://fda-docs.vercel.app/

## Core Principles

1. **Fractality**: Identical structure at all levels - components -> submodules -> domains -> applications
2. **Layer Separation**: Strict separation - repositories -> model -> controller -> state -> UI
3. **Explicit Contracts**: Every file has a strictly defined role and exports
4. **Framework-agnostic**: Works with SvelteKit, Next.js, Nuxt, etc.

## Architecture Layers (Bottom to Top)

| Layer | Files | Responsibility | Rules |
|-------|-------|----------------|-------|
| Repo | `lib/server/repo/*` | External data sources | No business logic |
| Model | `model.server.ts`, `schema.ts` | Data logic, CRUD | No rich business logic, no UI |
| RPC | `rpc.ts` | API endpoints | Uses models, no UI |
| Controller | `controller.ts`, `controller.svelte.ts` | State management | No external sources, no UI components |
| UI | `+page.svelte`, `ui/` | Display, input | No direct repo/rpc/model imports |

## Dependency Rules

- UI imports ONLY from: controller/stores, types, constants, ui/, lib/ui/
- Controller imports from: rpc, model, types, constants, lib/*
- Model imports from: repo, schema, types, lib/*
- RPC imports from: model, repo, types, lib/*
- repo imports from: external APIs, lib/*

NEVER:
- UI -> repo (direct)
- UI -> model.server (direct)
- UI -> rpc (direct)
- Model -> UI
- RPC -> UI
- repo -> UI

## Module Structure

Every domain/module MUST have:

Required:
- `+page.svelte` - page component
- `+page.server.ts` - load function + actions
- `rpc.ts` - RPC functions for cross-domain calls
- `model.server.ts` - data operations
- `controller.ts` or `controller.svelte.ts` - state + utilities
- `index.ts` - public API (exports from model, rpc, controller, types, constants)

Optional:
- `+layout.svelte` + `+layout.server.ts`
- `types.ts` - TypeScript interfaces
- `constants.ts` - constants/enums
- `utils.ts` - helpers
- `policy.ts` - authorization
- `templates.ts` - form schemas
- `schema.ts` - local ORM schema (rare)
- `ui/` - module-specific components

## Submodule Types

- `module/_sub/` - internal submodule (no route, prefix with _)
- `module/sub/` - public submodule (has route)

Both have the same internal structure as modules.

## File Contracts

### schema.ts
```typescript
// ONLY ORM table definitions
export const users = pgTable(...)
```

### model.server.ts
```typescript
// ONLY data operations via repo
export const getUser = async (id: string) => { ... }
export const createUser = async (data: CreateUserInput) => { ... }
```

### rpc.ts
```typescript
// ONLY API handlers
export const authenticateUser: Rpc<'auth/authenticate'> = async ({ email, password }) => { ... }
```

### controller.ts / controller.svelte.ts
```typescript
// ONLY reactive state and handlers

// Svelte 5 runes (preferred)
class UserController {
  user = $state<User | null>(null)
  async login(email: string, password: string) { ... }
}
export const userController = new UserController()

// Svelte 4 stores (legacy)
export const userStore = writable(null)
export const login = async (email: string, password: string) => { ... }
```

### +page.svelte
```svelte
<!-- ONLY markup, imports controller -->
<script>
  // Svelte 5 runes
  import { userController } from './controller.svelte'

  // Svelte 4 stores
  import { userStore, login } from './controller'
</script>
```

### policy.ts
```typescript
// ONLY access rules
export const canEditUser = (user: User, target: User) => boolean
```

### utils.ts
```typescript
// ONLY helpers
export const formatUser = (user: User) => string
```

### constants.ts
```typescript
// ONLY const/enum
export const MAX_SIZE = 1024
```

### types.ts
```typescript
// ONLY types
export interface User { ... }
```

### index.ts
```typescript
// Central export - MUST exist
export * from './model.server'
export * from './rpc'
export * from './controller'
export * from './types'
export * from './constants'
```

## Cross-Domain Communication

ALWAYS use RPC exports:
```typescript
// Good: importing from another domain
import { getProductById } from '../products/rpc'
```

NEVER import model directly from another domain.

## Creating a New Domain

When asked to create a new domain/module:

1. Ask what framework is being used (SvelteKit/Next/Nuxt)
2. Create folder structure based on framework routing
3. Add required files: +page, +page.server, rpc, model.server, controller, index
4. Add optional files as needed: types, constants, utils, policy, ui/
5. Ensure index.ts exports all public API
6. Verify dependency rules are followed
7. Use checklist to validate

## Validation Rules

When reviewing code, check:

1. Every module has index.ts
2. UI doesn't import repo/model/rpc directly
3. No UI imports in model/rpc layers
4. +layout.server.ts has matching +layout.svelte
5. File contracts are respected (each file exports only its role)
6. Cross-domain imports use rpc.ts
7. Reusable UI is in lib/ui/, not module ui/

## Framework Mappings

| Concept | SvelteKit | Next.js | Nuxt |
|---------|-----------|---------|------|
| Page | `+page.svelte` | `page.tsx` | `index.vue` |
| Layout | `+layout.svelte` | `layout.tsx` | `layout.vue` |
| Server Load | `+page.server.ts` | `page.server.tsx` | `setup.ts` |
| Server Actions | `+page.server.ts` (actions) | `actions.ts` | `server/` |
| API Routes | `+server.ts` | `route.ts` | `/server/api/` |
| RPC | `rpc.ts` | `rpc.ts` | `rpc.ts` |
| Model | `model.server.ts` | `model.ts` | `model.ts` |
